# Test Data Architecture

## Overview

The `test_data` package is the dedicated test-data preparation layer of the
EcommerceAPI framework.

Its purpose is to make test data:

- reusable
- readable
- isolated from network/database concerns
- customizable per scenario
- safe to provision and clean up
- reusable across REST API, GraphQL, and Playwright UI tests

In software testing, this style is commonly associated with the
**Object Mother** and **Test Data Factory / Builder** patterns.

The architecture used by this project goes a step further by separating
**data generation**, **scenario customization**, **system provisioning**,
**resource ownership**, and **pytest lifecycle management**.

The key principle is:

> **Tests should describe the data that matters to the scenario, while the
> test-data architecture supplies everything else.**

---

# Why Do We Need a Test Data Layer?

Without a dedicated test-data architecture, tests quickly become filled with
large, repetitive payloads.

For example, a customer test should not normally need to contain all of this
just to test one business rule:

```python
customer = {
    "email": "john123@example.com",
    "password": "Password123!",
    "username": "john123",
    "first_name": "John",
    "last_name": "Smith",
    "billing": {
        "first_name": "John",
        "last_name": "Smith",
        "address_1": "123 Main Street",
        "city": "Madrid",
        "state": "M",
        "postcode": "28001",
        "country": "ES",
        "email": "john123@example.com",
        "phone": "612345678",
    },
    "shipping": {
        "first_name": "John",
        "last_name": "Smith",
        "address_1": "123 Main Street",
        "city": "Madrid",
        "state": "M",
        "postcode": "28001",
        "country": "ES",
    },
}
```

If 50 tests need customers, this approach creates large amounts of
duplicated setup code.

Instead, a test should express only what is relevant:

```python
customer = (
    CustomerBuilder()
    .with_email("existing@example.com")
    .build()
)
```

Or:

```python
customer = (
    CustomerBuilder()
    .without_billing()
    .build()
)
```

Everything else can be generated automatically.

This follows the **"Only Care About What Matters"** principle:

> A test should explicitly define the data that is important to the scenario
> and allow irrelevant data to be generated by the test-data layer.

---

# Architectural Principles

The `test_data` architecture follows several important principles.

## 1. Data generation is separate from system interaction

Factories and builders prepare data **in memory**.

They do not:

- make HTTP requests
- access WooCommerce
- access the database
- create pytest fixtures
- perform cleanup
- depend on test execution state

They produce a plain Python dictionary.

For example:

```python
dict[str, Any]
```

This is a **blueprint** for a resource, not the resource itself.

A useful mental model is:

> **Factory / Builder cook the recipe. Provisioner turns on the stove.**

---

## 2. Domain models remain domain models

Pydantic models belong to their respective domain.

For example:

```text
EcommerceAPI/src/
└── customers/
    └── models/
        └── customer_model.py
```

`CustomerModel` represents the structure of a customer returned by the API.

It is not a replacement for the test-data factory.

The distinction is:

```text
CustomerModel
    ↓
"What does a valid Customer API object look like?"

CustomerFactory / CustomerBuilder
    ↓
"How do I generate data with which I can create a Customer?"
```

This prevents the test-data layer from creating competing versions of the
domain model.

---

# Test Data Architecture

The architecture is composed of the following responsibilities:

| Component | Responsibility | Network Call? |
|---|---|---:|
| **Factory** | Generate valid default data | ❌ |
| **Builder** | Customize data for a scenario | ❌ |
| **Provisioner** | Create/update real system state | ✅ |
| **Ownership** | Track who owns a resource | ❌ |
| **Seeds** | Provide stable environment baseline | Usually setup-time |
| **Cleanup** | Remove only resources owned by the test | ✅ |
| **Fixtures** | Provide pytest-facing lifecycle/interface | Indirectly |
| **Helper/API** | Execute domain/system operations | ✅ |

The architecture is intentionally layered rather than placing all
responsibilities in one fixture or helper.

# The Complete Pipeline

At a high level, valid test-data creation follows this lifecycle:

```text
                         TEST
                           │
                           ▼
                       FIXTURE
                           │
                           ▼
                       BUILDER
                           │
                           ▼
                       FACTORY
                           │
                           ▼
                 In-memory test data
                    dict[str, Any]
                           │
                           ▼
                     PROVISIONER
                           │
                           ▼
                    DOMAIN HELPER
                           │
                           ▼
                      DOMAIN API
                           │
                           ▼
                       WOOCOMMERCE
                           │
                           ▼
                  Created server object
                           │
                           ▼
                 Ownership registration
                           │
                           ▼
                         TEST
                           │
                           ▼
                        CLEANUP
```

The important architectural boundary is between **data preparation** and
**real system state**.

The test-data layer prepares the data:

```text
Builder → Factory
```

The provisioning/API layer creates real state:

```text
Provisioner → Helper → API → WooCommerce
```

The pytest fixture connects these responsibilities and owns the setup
lifecycle:

```text
Fixture → Builder → Factory → Provisioner → Helper/API
                         ↓
                  validated response
                         ↓
                  ownership registration
                         ↓
                     clean dict
```

# The Core Creation Flow

For a customer, the fundamental creation flow can be understood as three
major responsibilities: data preparation, system provisioning, and pytest
lifecycle management.

| Layer | Responsibility | Network Call? | Output |
|---|---|---:|---|
| **1. Builder / Factory** | Generate and customize valid creation data | ❌ No | Python dictionary |
| **2. Provisioner → Helper / API** | Cross the system boundary and execute the request against WooCommerce | ✅ Yes | `HttpResponse` / API response |
| **3. Fixture** | Validate setup, register ownership, and expose clean data to the test | Indirectly | Verified Python dictionary |

### Layer 1 — Builder / Factory

Creates a payload entirely in memory.

Example:

```python
customer_data = (
    CustomerBuilder()
    .with_first_name("John")
    .without_billing()
    .build()
)
```

No HTTP request occurs.

The result is simply data:

```python
{
    "email": "...",
    "password": "...",
    "username": "...",
    "first_name": "John",
    "last_name": "...",
    "billing": ...,
    "shipping": ...
}
```

### Layer 2 — Provisioner → Helper / API

The prepared data crosses the system boundary through the **Provisioner**.

The provisioner receives the Builder/Factory output, delegates the actual
domain operation to the existing Helper/API architecture, and returns the
resulting `HttpResponse` to the fixture.

Conceptually:

```python
customer_data = CustomerBuilder().build()
response = customer_provisioner.provision(customer_data)
```

Internally, the Provisioner delegates to the existing domain helper:

```python
response = customer_helper.create_customer(
    return_http_response=True,
    **customer_data,
)
```

This is where the physical network operation occurs.

### Layer 3 — Fixture

The pytest fixture acts as the test-facing gatekeeper.

It can:

1. build and provision the required valid data
2. verify the expected HTTP status
3. extract the response JSON
4. validate the resulting domain object
5. register the created resource for cleanup
6. return a clean object to the test

The test therefore does not need to understand raw HTTP response handling.

# Factory

## Responsibility

The **Factory** generates valid default data.

Its job is to answer:

> "Give me a valid customer/product/order/etc. creation payload."

A factory should:

- generate valid defaults
- generate collision-resistant test data
- use shared generic data generators
- provide sensible domain defaults
- accept explicit overrides where appropriate
- return plain creation data
- remain independent from pytest
- remain independent from HTTP
- remain independent from the database
- remain independent from cleanup

A factory should **not**:

- call an API
- create database records
- delete resources
- access pytest fixtures
- register cleanup
- contain test lifecycle logic

Example:

```python
customer = CustomerFactory().build()
```

The result is data in memory.

---

# Builder

## Responsibility

The **Builder** provides scenario-specific customization.

Its job is to answer:

> "Give me a valid customer, but change the parts relevant to this scenario."

Example:

```python
customer = (
    CustomerBuilder()
    .with_email("existing@example.com")
    .build()
)
```

Another example:

```python
customer = (
    CustomerBuilder()
    .without_billing()
    .with_first_name("John")
    .build()
)
```

The builder collects overrides and delegates final data generation to the
factory.

This allows tests to remain expressive without manually constructing the
entire payload.

## Customer Builder vs Customer State Builder

The customer domain has two intentionally different builder concepts.

### `CustomerBuilder`

`CustomerBuilder` prepares **complete creation data for a new customer**.
It works with `CustomerFactory` so unspecified fields receive valid defaults.

```python
customer_data = (
    CustomerBuilder()
    .with_email("known@example.com")
    .build()
)
```

```text
CustomerBuilder
      ↓
CustomerFactory
      ↓
complete creation payload
      ↓
CustomerProvisioner
      ↓
new customer
```

### `CustomerStateBuilder`

`CustomerStateBuilder` prepares **partial state changes for an existing
customer**. It does not call a factory and does not generate unrelated fields.

```python
customer_state = (
    CustomerStateBuilder()
    .with_first_name("QAUpdated")
    .with_email("updated@example.com")
    .build()
)
```

Result:

```python
{
    "first_name": "QAUpdated",
    "email": "updated@example.com",
}
```

```text
CustomerStateBuilder
      ↓
partial state/change
      ↓
CustomerStateProvisioner
      ↓
existing customer
```

The distinction is deliberate:

> **CustomerBuilder answers: "What should this new customer look like?"**

> **CustomerStateBuilder answers: "What should change on this existing customer?"**

A state builder must not silently generate a complete customer or overwrite
fields that the scenario did not ask to change.

### Why use a Builder?

Imagine a test for duplicate email handling.

The important piece of data is the email:

```python
.with_email(existing_email)
```

The test should not have to care about:

- random first name
- random last name
- password
- username
- billing address
- shipping address
- phone number

Those are implementation details of the default test data.

---

# "Only Care About What Matters"

This is one of the most important principles in the architecture.

A test should make its intent visible.

### Bad

```python
customer = {
    "email": existing_email,
    "password": "Password123!",
    "username": "test_user_123",
    "first_name": "John",
    "last_name": "Smith",
    "billing": {...},
    "shipping": {...},
}
```

The reader has to determine which part matters.

### Better

```python
customer = (
    CustomerBuilder()
    .with_email(existing_email)
    .build()
)
```

The test communicates:

> "The email is the important part of this scenario."

Everything else is generated automatically.

This becomes especially valuable as the test suite grows.

# Generic Data Utilities

Generic random-data generation belongs in the shared utility layer.

For example:

```text
EcommerceAPI/src/utils/
└── generic_utilities.py
```

The utility layer should provide **generic primitives**, such as:

```python
generate_random_email()
generate_random_password()
generate_random_first_name()
generate_random_last_name()
generate_random_username()
generate_random_phone()
generate_random_city()
generate_random_state_code()
generate_random_postcode()
generate_random_street_address()
generate_random_address()
```

It can also contain already-existing generators such as:

```python
generate_random_string()
generate_random_combination()
safe_product_name()
generate_random_coupon_code()
```

The important distinction is:

```text
Generic Utility
    ↓
"Generate a random city."

Customer Factory
    ↓
"Use that city as part of a WooCommerce customer address."

Product Factory
    ↓
"Use generic generators to construct a product."

Order Factory
    ↓
"Use generic generators to construct order-related data."
```

The utility layer should not become a collection of
`generate_random_customer()` or `generate_random_product()` functions.

That domain composition belongs in the factories.

---

# Builder + Factory Relationship

The relationship can be visualized as:

```text
             Generic Utilities
                    │
                    ▼
             CustomerFactory
             ┌───────────────┐
             │ valid defaults│
             └───────┬───────┘
                     │
                     ▼
             CustomerBuilder
             ┌───────────────┐
             │ scenario      │
             │ overrides     │
             └───────┬───────┘
                     │
                     ▼
              Customer Data
               dict[str, Any]
```

The builder should not duplicate the factory's generation logic.

The factory should not contain test-specific scenario logic.

This separation keeps both components reusable.

# Provisioner

## Responsibility

The **Provisioner** crosses the boundary from prepared data to real system
state.

Its job is to answer:

> "Take this already-prepared test data and make it exist in the system in the required state."

For example:

```text
CustomerBuilder
      ↓
customer_data
      ↓
CustomerProvisioner
      ↓
CustomersHelper
      ↓
CustomersApi
      ↓
WooCommerce
```

The provisioner:

- accepts data already prepared by the Factory/Builder;
- delegates the creation operation to the existing domain Helper/API layers;
- returns the framework `HttpResponse` to the fixture;
- does not generate or customize test data;
- does not validate the HTTP status;
- does not validate the response schema;
- does not register cleanup;
- does not access pytest fixtures or the database.

The **fixture** remains the gatekeeper for setup validation and ownership
registration.

The Provisioner deliberately does not perform raw HTTP requests when the
domain Helper/API already provide that capability.

---

# Ownership

## Responsibility

Creating a resource is not enough.

The framework must also know:

> "Who created this resource, and who is responsible for removing it?"

This is the purpose of **Ownership**.

A resource created by a test should be considered **test-owned**.

A stable seed created during environment provisioning should generally not be
treated as a normal test-owned resource.

Conceptually:

```text
Seed Customer
    │
    └── Environment-owned
         └── Must survive normal test cleanup


Dynamic Customer
    │
    └── Test-owned
         └── Eligible for cleanup
```

Ownership is particularly important for:

- parallel test execution
- isolated test runs
- cross-domain resources
- UI/API combined tests
- preventing accidental deletion of seed data

---

# Cleanup

## Principle

Cleanup must remove **only resources owned by the test**.

This is a critical safety rule.

The framework should never blindly delete:

```text
"all customers created during setup"
```

or:

```text
"all customers matching a username pattern"
```

Instead, it should know which resources the current test created.

Conceptually:

```text
Test starts
    ↓
Create customer
    ↓
Register customer ID as owned
    ↓
Test runs
    ↓
Test finishes
    ↓
Cleanup owned customer
```

If the test creates:

```text
Customer A
Product B
Coupon C
```

the ownership registry should know that these resources belong to that test
and can therefore be cleaned up.

Stable environment seeds remain untouched.

---

# Seeds

## Responsibility

**Seeds** provide the stable baseline required by the test environment.

Examples include:

- predefined UI customer personas
- baseline products
- environment configuration data
- users required for authentication scenarios

Seeds are different from dynamic test data.

For example:

```text
Environment Setup
       │
       ├── UI_CUSTOMER_USERNAME
       ├── UI_CUSTOMER_NO_ADDRESS_USERNAME
       └── UI_CUSTOMER_PROFILE_USERNAME
```

These are stable personas used by UI scenarios.

They should survive normal test cleanup.

### Seed vs Dynamic Data

| Data | Purpose | Lifecycle |
|---|---|---|
| **Seed** | Stable environment baseline | Created by environment setup |
| **Factory data** | Fresh scenario data | Generated per test/use |
| **Provisioned data** | Real system state | Created by test/provisioner |
| **Owned data** | Resources created by a test | Eligible for cleanup |

This distinction prevents the cleanup layer from destroying the environment
that the UI suite depends on.

---

# Fixtures

## Responsibility

Fixtures provide the **pytest-facing interface**.

They should hide infrastructure details from tests.

For example, a test should ideally be able to write:

```python
def test_customer_can_be_created(create_valid_customer):
    customer = create_valid_customer()
```

rather than manually handling:

```python
response = ...
assert response.status_code == 201
payload = response.json()
validate(...)
register_for_cleanup(...)
```

The fixture is the lifecycle boundary between pytest and the underlying
test-data architecture.

For the current customer implementation, `create_valid_customer` performs:

```text
Fixture
   ↓
CustomerBuilder
   ↓
CustomerFactory
   ↓
CustomerProvisioner
   ↓
CustomersHelper
   ↓
CustomersApi
   ↓
WooCommerce
   ↓
HttpResponse
   ↓
201 validation
   ↓
response-body/domain validation
   ↓
ownership registration
   ↓
validated customer dict
```

The fixture does not generate customer data itself and does not rely on
`CustomersHelper` to generate credentials.

---

# Fixtures Are Not the Factory

A common architectural mistake is to put everything into `conftest.py`.

That eventually produces large fixtures containing:

- random data generation
- payload construction
- HTTP requests
- validation
- cleanup
- scenario-specific logic

This architecture intentionally avoids that.

Instead:

```text
Fixture
   │
   ├── lifecycle/interface
   │
   ▼
Provisioner
   │
   ├── system state
   │
   ▼
Helper/API
   │
   ├── HTTP
   │
   ▼
WooCommerce
```

while:

```text
Builder
   │
   ▼
Factory
   │
   ▼
Generic Utilities
```

remain responsible for data preparation.

---

# Negative Testing

The separation is especially valuable for negative tests.

A happy-path fixture may deliberately guarantee valid data.

A negative test often needs to violate one specific rule.

For example:

```python
customer_data = (
    CustomerBuilder()
    .with_email("not-an-email")
    .build()
)
```

The builder can prepare the scenario data without automatically provisioning
it.

The test can then send the intentionally invalid payload through the
appropriate lower-level API path.

This means the data-preparation architecture does not force every test through
a "valid customer" fixture.

---

# Reuse Across REST, GraphQL and UI

One of the major benefits of keeping factories and builders independent from
the network is reuse.

The same customer blueprint can be used by:

```text
                 CustomerBuilder
                        │
              ┌─────────┼─────────┐
              │         │         │
              ▼         ▼         ▼
            REST     GraphQL     UI
              │         │         │
              ▼         ▼         ▼
          WooCommerce / WordPress
```

For example, the same builder can prepare:

```python
customer = (
    CustomerBuilder()
    .with_first_name("John")
    .with_last_name("Smith")
    .build()
)
```

REST can provision it through the API.

GraphQL can provision or manipulate it through GraphQL.

Playwright can use the same data to populate UI fields.

The builder does not care which system eventually consumes the data.

This is possible precisely because the builder does **not** contain network
logic.

# Cross-System Test Data

This architecture also supports tests where one interface prepares the data
and another interface consumes it.

For example:

```text
REST API
   │
   │ provision customer
   ▼
WooCommerce
   │
   │ customer now exists
   ▼
Playwright UI
   │
   │ log in / browse / checkout
   ▼
UI assertion
```

The test-data layer should make this possible without coupling the data
generation itself to either REST or UI.

# Object Mother vs Factory + Builder

The terminology is worth understanding.

## Object Mother

An **Object Mother** is a test-data pattern where reusable methods provide
preconfigured objects for common scenarios.

For example:

```python
customer = TestCustomers.standard_customer()
```

or:

```python
customer = TestCustomers.customer_without_address()
```

This can be very useful when a test suite has well-known personas.

## Factory

A **Factory** focuses on creating valid objects/data.

```python
customer = CustomerFactory().build()
```

The factory usually owns the defaults and valid-data generation rules.

## Builder

A **Builder** provides fluent or structured customization.

```python
customer = (
    CustomerBuilder()
    .with_email(existing_email)
    .without_billing()
    .build()
)
```

### This Project

This project is primarily using the:

> **Data Factory + Builder pattern**

with additional:

- Provisioner
- Ownership
- Seed
- Cleanup
- Fixture

layers.

Some stable personas may also resemble the Object Mother concept, especially
when the framework exposes predefined environment-level test identities.

The patterns are not mutually exclusive.

---

# What Each Layer Must Not Do

Keeping boundaries explicit is important.

| Layer | Must Not |
|---|---|
| **Generic Utilities** | Know about customers, WooCommerce, pytest, or APIs |
| **Factory** | Make network/database calls or manage cleanup |
| **Builder** | Make network/database calls or own test lifecycle |
| **Provisioner** | Reimplement generic random-data generation |
| **Helper/API** | Become the test-data factory |
| **Ownership** | Generate test data |
| **Seeds** | Be treated as disposable test-owned resources |
| **Fixture** | Become a giant data-generation/HTTP implementation |
| **Domain Model** | Become a test-data factory |

These boundaries prevent responsibilities from slowly leaking between layers.

# Design Rules

The following rules should guide future development.

### Rule 1 — Tests express intent

Prefer:

```python
CustomerBuilder().with_email(existing_email).build()
```

over a large manually constructed payload when only the email matters.

### Rule 2 — Defaults are automatic

Tests should not have to specify irrelevant data.

### Rule 3 — Explicit overrides always win

If a test supplies a value, the factory must respect it.

### Rule 4 — Data preparation is pure

Factory and builder operations should prepare data in memory.

### Rule 5 — Network interaction belongs below the test-data preparation layer

Provisioning belongs to the provisioner/helper/API architecture.

### Rule 6 — Ownership is explicit

Only resources owned by a test should be eligible for normal cleanup.

### Rule 7 — Seeds are protected

Environment-level seed data must not be accidentally deleted by test cleanup.

### Rule 8 — Reuse generic generators

Do not introduce multiple random-data libraries for the same purpose.

Generic utilities should provide reusable primitives; factories should compose
them.

### Rule 9 — Do not over-generalize

Add a generic utility when a real reusable need exists.

Do not create abstractions merely because a future domain might need them.

### Rule 10 — Keep domain models canonical

Do not create competing Pydantic models inside `test_data` when an existing
domain model already represents the relevant API contract.

# Current Implementation Status

The customer domain is currently the reference implementation for this
architecture.

The following pieces are now implemented and verified by the existing REST
customer test suite:

- Customer Factory
- Customer Builder
- Customer Provisioner
- Ownership / cleanup integration
- `create_valid_customer` fixture integration
- `CustomersHelper` refactored so it no longer generates test data

The public test-facing contract of `create_valid_customer` remains unchanged:

```python
customer = create_valid_customer()
```

The fixture returns a validated customer dictionary and owns setup validation
and cleanup registration.

The `CustomersHelper` is now responsible only for customer API/domain
orchestration. Test-data generation belongs to the Factory/Builder layer, and
system provisioning belongs to the Provisioner.

# Development Strategy

The architecture is implemented incrementally.

The customer reference implementation has now completed the initial lifecycle:

```text
1. Architecture contract                    ✅
       ↓
2. Customer Factory                         ✅
       ↓
3. Customer Builder                         ✅
       ↓
4. Customer Provisioner                     ✅
       ↓
5. Ownership / Cleanup integration          ✅
       ↓
6. Customer fixture integration             ✅
       ↓
7. CustomersHelper refactor                 ✅
       ↓
8. Customer State Builder                   ✅
       ↓
9. Customer State Provisioner               ✅
       ↓
10. First real test migration               ✅
       ↓
11. Product test data
       ↓
12. Coupon test data
       ↓
13. Order and cross-domain test data
       ↓
14. REST / GraphQL / UI cross-system scenarios
```

The customer state pattern is now established by a real update test.

The important distinction is:

```text
CustomerBuilder
    → complete creation data for a new customer

CustomerStateBuilder
    → partial state/change for an existing customer

CustomerProvisioner
    → create a new customer

CustomerStateProvisioner
    → establish state on an existing customer
```

The operation under test must remain visible in the test. A test for customer
update behavior should not hide the PUT operation inside a state provisioner
when that PUT is the behavior being verified.

We should continue to avoid large speculative abstractions before there is a
real requirement for them.

# Example Mental Model for New Contributors

When deciding where new code belongs, ask:

### "I need a random value."

→ **Generic Utility**

```python
generate_random_phone()
```

### "I need a valid Customer creation payload."

→ **Factory**

```python
CustomerFactory().build()
```

### "I need a Customer payload with one special condition."

→ **Builder**

```python
CustomerBuilder().without_billing().build()
```

### "I need to change specific fields on an existing Customer."

→ **Customer State Builder**

```python
(
    CustomerStateBuilder()
    .with_first_name("QAUpdated")
    .with_email("updated@example.com")
    .build()
)
```

This produces only the state that should change. It does not generate a new
customer.

### "I need that Customer to actually exist in WooCommerce."

→ **Provisioner**

```python
customer_provisioner.provision(customer_data)
```

### "I need a valid customer through the normal pytest setup lifecycle."

→ **Fixture**

```python
customer = create_valid_customer()
```

### "I need to know whether the test is responsible for deleting it."

→ **Ownership**

```text
test-owned → cleanup eligible
seed-owned → protected
```

### "I need pytest to manage the lifecycle."

→ **Fixture**

```python
def test_something(create_valid_customer):
    ...
```

This mental model should make the architecture approachable for both
experienced engineers and newcomers.

# Summary

The `test_data` architecture exists to solve a fundamental automation problem:

> **Tests need realistic, isolated, maintainable data without becoming
> responsible for constructing and managing every detail themselves.**

The project separates this problem into explicit responsibilities:

```text
┌──────────────────────────────────────────────────────────┐
│                    TEST SCENARIO                         │
└──────────────────────────┬───────────────────────────────┘
                           │
                           ▼
                    ┌─────────────┐
                    │   Fixture   │
                    │ lifecycle   │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │   Builder   │
                    │ customization│
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │   Factory   │
                    │ valid data  │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │  Utilities  │
                    │ primitives  │
                    └─────────────┘

                           │
                           │ data
                           ▼

                    ┌─────────────┐
                    │Provisioner  │
                    │real state   │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │Helper / API │
                    │HTTP         │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │ WooCommerce │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │ Ownership   │
                    │ + Cleanup   │
                    └─────────────┘
```

The result is a test-data system that is:

- readable
- reusable
- composable
- isolated
- maintainable
- safe for cleanup
- suitable for parallel execution
- reusable across REST, GraphQL, and UI automation
- understandable to new contributors

This document is intentionally a **living architecture document**. As the
test-data system evolves, examples, responsibilities, package structure, and
rules should be updated here so that the README remains the authoritative
guide for the `test_data` feature.
